# Independent JOSE evaluation

This package generates deterministic synthetic compact JWE and JWS candidates
from the JOSE serialization specifications and PyCA cryptography primitives.
It never imports recognizer patterns, derives labels from detections, reads live
keys, or accesses the user's stored token. Structure labels and exposure labels
are separate; a valid public example remains a format positive.

## Frozen corpus

`split_manifest.json` is the preserved V1 artifact. It is superseded for
independent template-holdout claims because its nominal families reused actual
render recipes. Do not regenerate or use its detector results to select V2
thresholds. The active manifest is `split_manifest_v2.json`, generated by
`corpus_v2.py` and frozen by `freeze_v2.py`:

```sh
python -m tools.recognizer_eval.freeze_v2
python -m tools.recognizer_eval.freeze_v2 --check
```

V2 contains 13,000 main examples: 2,000 intact supported JWE positives,
1,000 intact JWS candidates (positive only for the separate JWS target), and
10,000 negatives clean of either compact JOSE form. The JWE target's negative
population is 11,000 when JWS candidates are included; the class-conditional
JWE table excludes those 1,000 format-positive JWS cases. The JOSE union table
uses 3,000 JOSE-positive examples and 10,000 clean negatives. Dev has 1,600
JWE, 800 JWS, and 8,000 clean negatives; holdout has 400, 200, and 2,000.

Each case has a fixed label, Unicode codepoint span, unique domain-separated
seed group, and concrete normalized rendering fingerprint. Holdout wrapper
and protected-header recipes are separate from dev recipes. The freeze check
compares actual normalized surfaces against V1 dev, including V1 auxiliary
examples, and requires zero overlap. The separate 160-case context/preset set
has its own four actual templates per slice, domain-separated values, and 80
dev/80 holdout cases. Its holdout templates are audited against V1 dev too.

The 120 malformed/unsupported cases and 72 PDF/DOCX/XLSX files are shared
integration regressions, not independent holdout performance samples. An
adversarial input error never becomes a TN. In document gates, an extraction
failure or missing positive token is a positive FN/omission; a failed negative
extraction is incomplete, never a TN.

Replace `RUN_ROOT` and `SOURCE_ROOT` with approved private run and source
directories. Run the dedicated suite with Python 3.11 through the required heavy-command
wrapper:

```sh
python3 RUN_ROOT/run-heavy.py evaluation -- \
  RUN_ROOT/venvs/evaluation/bin/python \
  -m pytest -q tools/recognizer_eval/tests
```

## Detector profiles and metrics

An evaluation profile names a public detector factory, raw-candidate options,
and fixed review/block comparison points. Presidio profiles use
`score-threshold: "0"` only in this evaluation harness so raw candidate scores
are retained before production filtering. All profiles pin `ner-mode` to
`pattern-only`. `context-mode: none` is used for the no-context and baseline
comparisons; the paired preset profiles isolate context from entity
registration. The lead froze review at 0.35 and the numeric block-score
comparison at 1.0 using V2 development only; JOSE entities are not assigned
generic production block severity.

The text report separates JWE case metrics, the JWE-vs-clean-negative
class-conditional denominator, JWE alerts on known JWS candidates, JWS target
metrics, and the JOSE union. Raw candidate exact/overlap span scores are
reported separately from review-threshold spans. Actual returned `block`
severity is separate from the numeric high-score comparison. Wilson intervals
are included for case proportions; stratified template-family bootstrap
intervals expose grouped variation. PR average precision and ROC AUC use raw
candidate ranking values, not calibrated probabilities. When JWE/JWS
candidates have only one distinct nonzero score level, average precision is
presence-equivalent and ROC AUC is omitted. Binary Gitleaks results have no
invented scores, block policy, AUC, or spans.

The CLI defaults to `--split dev`. Holdout and combined runs are rejected
unless the lead-owned `control/interfaces/contract.json` authorizes them.
Contract revision 10 authorized one final V2 holdout pass, now recorded in
`REPORT.md` and `HOLDOUT_ARTIFACTS.json`. Do not repeat that sealed run; the
index records its exact commands and outputs. The command below is a DEV-safe
reproducibility example:

```sh
python3 RUN_ROOT/run-heavy.py evaluation -- \
  RUN_ROOT/venvs/evaluation/bin/python \
  -m tools.recognizer_eval.evaluate \
  --profile /path/to/frozen-profile.json \
  --source-root /path/to/lead-integrated-checkout \
  --manifest tools/recognizer_eval/split_manifest_v2.json \
  --split dev \
  --output /path/to/private-artifacts/metrics.json
```

Gitleaks 8.30.1 has two one-invocation DEV baselines over the same staged
files. The stock run uses the built-in rules with inherited Gitleaks config
settings removed:

```sh
python3 RUN_ROOT/run-heavy.py evaluation -- \
  RUN_ROOT/venvs/evaluation/bin/python \
  -m tools.recognizer_eval.gitleaks \
  --gitleaks /path/to/gitleaks \
  --manifest tools/recognizer_eval/split_manifest_v2.json \
  --split dev \
  --output /path/to/private-artifacts/gitleaks-stock-metrics.json
```

The shipped LeakGuard binary baseline adds `src/leakguard_core/rules.toml` to
the built-in rules. Its output records the exact config SHA-256:

```sh
python3 RUN_ROOT/run-heavy.py evaluation -- \
  RUN_ROOT/venvs/evaluation/bin/python \
  -m tools.recognizer_eval.gitleaks \
  --gitleaks /path/to/gitleaks \
  --config src/leakguard_core/rules.toml \
  --manifest tools/recognizer_eval/split_manifest_v2.json \
  --split dev \
  --output /path/to/private-artifacts/gitleaks-shipped-rules-metrics.json
```

Both outputs measure binary file-level rule presence, not token classification.
The `jwt` rule is counted for the JWS target from its rule ID regardless of
case labels; any rule hit contributes to the JOSE-union detection. Block and
actionability severity are unavailable, and no spans or AUC are fabricated.

Metrics JSON contains case IDs, labels, offsets, detector scores, timings, and
hashes, never matched token values or source text. The review sweep is
predeclared at 0.05, 0.35, 0.40, 0.50, 0.80, 0.93, 0.96, 0.99, and 1.00 and
is development-only. Unsupported or malformed compact candidates remain in
the separate adversarial regression set, never silently relabeled benign.

## Limits

These synthetic results do not estimate production prevalence, cryptographic
validity, issuer, exposure, or severity. V2 holdout contains only eight JWE
families, four JWS families, and ten clean-negative families; even a zero-FP
sample of 2,000 clean negatives has a Wilson upper 95% FPR bound near 0.19%.
Family-cluster bootstrap intervals expose some recipe variation but cannot
represent real organizations or token distributions. Public valid JWEs are
format positives and are evaluated separately for block behavior.

The context/preset slice measures weak-pattern finance/identity recognition
with nearby terms, misleading numeric context, and field terms more than 96
characters away. It is not folded into JOSE structure performance. Numeric
identity-shaped negatives can still alert and this must remain visible in its
own slice.

Historical run reports/indexes `REPORT.md` and `HOLDOUT_ARTIFACTS.json` remain in
reviewed Git history and private evidence; they are omitted from the CLI release
source archive. This harness source is retained for review and new development
qualification; it does not make historical holdouts newly unseen.
